Runtime subsystem contract inventory

Read-only source inventory of the six runtime areas that the phase 0 ECS trace did not cover: ground and physics queries, GPU objects and geometry lifetime, events and input, declarative GUI and runtime callbacks, streaming and builders, and audio and process lifecycle. Scope and method

This inventory extends the completed ECS contract inventory and does not repeat its findings. It covers every place in the pinned Contravía tree that reaches one of the six runtime areas, plus the engine contract each reach depends on.

  • Systematic scan. 252 pinned Contravía .py files were parsed with Python's ast module; 223 import lines name manifoldx or a submodule. Attribute chains rooted at engine, self.engine, mx, and explicit private names were collected, then checked against 598 pinned engine .py files and 324 engine test files.
  • Call and impact checks. aegis map repo, aegis map callers and aegis map impact were run on the pinned engine tree for public definitions such as Engine.render_to_texture, Engine.on, Engine.system, Streamer.focus, QuadStreamer.focus and Audio.close. Counts from that tool are name-level and include engine tests; they were used to widen the search, not as proof of contract.
  • Pinned reads. Files were read with git show <sha>:<path>; the working tree was not the source. Every link below is a GitHub permalink to the pinned commit and line.
  • Classification. Regex classification over the pinned tree found 18 files touching ground or vehicle physics, 34 touching GPU resources or rendering, 17 touching events, systems or input, 9 touching GUI, 14 touching streaming or reload, and 7 touching audio. The sets overlap.

Full engine API coverage is larger than Contravía's reach. Compute, asynchronous event handlers, frame waiters and the interactive GUI widgets are recorded as engine contracts with zero or near-zero game consumers, not as game blockers.

Observed facts

  • Ground is one batched protocol call, not one call per wheel. The engine asks for all wheel samples in a single ground.height call per substep, then one ground.grip call, and adds one eight-corner height call only when the body is loose. The engine test at test_fleet.py:114 counts one call per upright step.
  • near is semantic, not advisory. The game's Surface.height uses it to choose among road, bridge and tunnel levels (surface.py:94). A native heightfield without the previous height cannot reproduce that choice.
  • Physics is a fixed 120 Hz loop inside a variable frame. Vehicles.advance runs floor(accumulator / DT) steps, caps a frame at 0.05 s and returns the count (fleet.py:124). The game's telemetry exposes substeps and bodies.
  • GPU creation is deferred, but the handles are created early. texture_array can exist before the device; write_layer and streamer draws are queued into the command buffer and run on the main thread. Geometry buffers are freed by _free_geometries only when no live entity uses them.
  • The game uses two real private engine refs in this area. EnvironmentMap._precompute and ._computed start and observe the IBL background job (atmosphere.py:176); engine._geometry_registry.release frees a retired figure's buffers (people.py:205).
  • One render-state setter is not deferred. set_sun, set_spot, enable_shadows and set_environment carry the deferred decorator; set_post assigns _post immediately and is absent from the pipeline version check (engine.py:1077). The game calls it from the parallel sky system (atmosphere.py:205). This is a source-level inconsistency to settle before phase 5; no runtime failure was observed or claimed.
  • Compute has no Contravía consumer. The 252-file scan found no manifoldx.compute import, no engine.compute call and no Compute subclass. It is an engine-only contract today.
  • Events are one frame late by design. emit queues; dispatch_pending runs at the start of the next frame; startup and shutdown are immediate. The game registers 12 custom events and never uses an async handler, a frame waiter or submit_process.
  • The only asynchronous game path is the IBL precompute. It uses engine.background and either polls _computed or calls Task.wait for an offline shot. No on_ready callback is used.
  • GUI runtime callbacks are private in the game. The game's click target is a Panel subclass that sets _is_gui_interactive and overrides _on_pointer_down (menu.py:45). It also calls _deferred.current and _deferred.defer to size a panel after deferred text lands (ui.py:190).
  • Widget writes are deferred while systems run. A write to an attached widget during a pipelined frame is queued, so the render never reads a half-changed field (widgets.py:45). The generic render-thread getter is ValueDisplay.refresh, called from the GUI pass; Contravía does not use it.
  • Streaming runs on two process pools and two caches. The quadtree and detail streamers take Builders(..., "process", warm=cells.warm); the game reads _ready, _selected and _distance for the curtain, stats and bench, and calls cancel on teleport and close on shutdown.
  • A Python reload rebuilds the scene and its GPU resources, not the window and device. Hot reload drops app modules, reruns the app, detaches the old engine and reuses the window and device. The game closes its streamers and builders in shutdown and keeps only engine.state plain data. The sound handle is the deliberate exception.
  • Audio is two spawned processes. The sound process mixes five buses; a separate music process pushes rendered chunks into a stream. The game keeps one sound process across reloads and terminates the music process before closing audio. On a normal exit it relies on the daemon flag, not on Game._shutdown.

Recommended decisions

  • Treat the batched Ground protocol as the phase 4 compatibility seam. Preserve one vectorized height(x, z, near) call and one grip(x, z) call per substep, with the same array shapes and near semantics. Before porting physics, decide whether the native solver calls the game's Python Ground or reads an uploaded terrain cache; do not replace the seam with a flat heightmap.
  • Keep wall segments and vehicle boxes as boundary arrays. The contact code expects (M, 2, 2) walls and footprint half-extents, not triangles. The three-round wall resolution and the impulse fields are part of the physics contract.
  • Preserve the GPU lifetime rules that the game already depends on. Texture handles may exist before the device; deferred writes apply on the main thread; read_texture returns a future with one or two frames of latency; geometry buffers are freed only when unreferenced. Treat the private registry release and IBL precompute as adaptation points, not as removable internals. Before phase 5, decide whether set_post must join the deferred set or the pipeline version check, since the game calls it from a parallel system.
  • Keep the Python GUI object model and dispatch pointer callbacks into it. The phase 5 runtime may own layout, hit testing and paint, but the game's click target is a Python Panel override. Either keep dispatching _on_pointer_down to Python or add a public callback surface before removing the private one. Keep per-frame pointer_over_gui reset and deferred widget writes.
  • Keep MeshData as the Python-side build result and map it to the SDK output explicitly. Preserve focus, cancel, close, the upload budget attributes and the process Builders lifetime. The streamer's private caches are known consumers, not public API.
  • Leave audio in Python unless the coordinator names a phase for it. Preserve the non-blocking control plane, the picklable factory rule, Audio.reload and the state-held sound reuse. Do not let the native engine's shutdown kill a process the game owns.
  • Close phase 0 source coverage with this document, not with parity. The six areas now have pinned consumer traces. Native physics, renderer, GUI, streaming and audio execution remain later phases, and no gate turns green from this inventory.

Static limitations and verification

  • No runtime validation. Nothing in this document was built, installed, executed, rendered, played or profiled. Test names are cited as static evidence that coverage exists; they were not run for this document.
  • Pinned sources only. The engine is b03be6e and Contravía is 72b9669. The shared game checkout was not used as the source. No line here describes a later working-tree state.
  • Name-based AST coverage. The scan collects attribute chains and import names. It does not type-infer a receiver through aliases or containers. A few private names therefore remain approximate; each one cited in the matrix was confirmed with git grep and git show.
  • Caller counts are a search aid. aegis map callers reports name-level matches and marks uncertain receivers with ?. The counts widened the search but are not used as proof of a contract.
  • The engine API is larger than Contravía's reach. Compute, async event handlers, frame waiters, submit_process, the interactive widget set and ValueDisplay have zero or no direct game consumers in the pinned tree. They are recorded as engine-only contracts and are not phase 0 game blockers.
  • Window evidence is bounded. The coordinator-reviewed native window probe proves a Linux Wayland/Vulkan hidden window, an actual resize event, two acquire/submit/present frames on the original main thread and ordered teardown. It does not prove visible scanout, the Python bridge, another operating system, shader or renderer parity, reload or audio. Its report is retained privately; no private host or path is reproduced here.
  • No authority to change contracts. This inventory records source behavior. It does not approve breaking public aliases, changing component dtypes, removing private refs without adaptation, or editing the migration tracker, spec or vision issue.

Open questions for coordinator decision

  1. Native ground data ownership at phase 4. Does the native solver call the game's Python Ground per substep, or does phase 4 require an uploaded terrain, road and tunnel representation? The source fixes the call shape but not the ownership. This decides whether the game's Surface rules stay entirely Python.
  2. GUI callback boundary at phase 5. Is the game's private Panel._on_pointer_down override a supported adaptation, or should the native runtime expose a public callback or event? The same question applies to _deferred, which the game uses for correct panel sizing in a pipelined frame.
  3. Audio placement. Audio is absent from the approved phase order. Does it stay Python through Move A, B and C, or does a later phase own it? The game's two spawned processes and its state-held Sound reuse need an explicit answer.
  4. Async and waiter parity scope. Are FrameWaiters, tick/delay/elapsed_at, async event handlers and Task.on_ready required in phase 3 parity even though Contravía uses none of them except Task.wait? If not, they should be named as engine-only paths, not silently skipped.
  5. Mesh data contract at phase 6. Is MeshData the Python-side builder contract that the SDK maps to CellRequest/BuildOutput, or do native builders receive a different shape? Which arrays may cross zero-copy, and which require an explicit copy?
  6. Compute parity scope. The game has no compute consumer. Is compute part of the shared parity suite because it is engine API, or outside the Contravía compatibility gate? Either answer is defensible; it should be written down before the gate is claimed.
